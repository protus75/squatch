## Summary
The ticket contradicts itself. It requires a public read-only Driver accessor on the composed pipeline or on Stages, but its fence leaves out `squatch/stages.py` and `squatch/merge.py`, which own both objects. The diff works around this with a hidden context variable that grabs whichever Driver is built first, which breaks the ticket's 'explicit' construction-seam requirement, and it also makes changes the ticket did not ask for.

## Findings
- correctness_review at squatch/driver.py:129: The ticket's Scope in says to expose the Driver through an explicit public read-only accessor on the composed production pipeline or Stages, and not to probe private `_driver`. The only production Driver lives in `Stages._driver` (squatch/stages.py:566), and the pipeline is built in squatch/merge.py. Both files are outside the Scope fence, so the criterion cannot be met inside the fence. The diff substitutes a hidden global: `Driver.__init__` registers itself into a context variable, and `DriverBinding.bind` keeps the first Driver created during composition. It relies on the unenforced fact that Stages builds its Driver before the diagnose Driver (squatch/diagnose.py:125). If that order changes, retro silently runs through the diagnosis-only Driver. The 'public Driver accessor' test (`DriverBinding.driver`) checks this side channel, not an accessor on the pipeline or Stages as the acceptance criterion requires. (paved road: Fix the plan and regenerate the ticket with `squatch/stages.py` (and `squatch/merge.py` if the accessor goes on the pipeline) inside the Scope fence. Then add an explicit read-only `driver` property on Stages or the composed pipeline, read it in `__main__._locked`, and delete the context-variable capture from `squatch/driver.py`.)
