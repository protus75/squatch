## Summary
The retro module, triggers, report lane, effect key, suppression and Drain hook all look right, and the checks pass. But `_drain` binds the production hook only when no pipeline is injected, unless the pipeline sets `retro_enabled`. So every named regression suite skips the forced post-merge retro, and the migration the ticket requires never happened.

## Findings
- correctness_review at squatch/__main__.py:215: The ticket says to bind the hook in `_drain` and to migrate the named regression suites (`tests/test_drain_reentry.py`, `tests/test_seed_successor.py`, `tests/test_drain_upgrade.py`, `tests/test_daemon_composition.py`, `tests/test_kill_cli_activation.py`, `tests/test_storm_hold.py`, `tests/test_storm_notification_activation.py`, `tests/test_restart_timers.py`, `tests/test_provider_cooldown_failover.py`, `tests/test_watchdog_activation.py`, `tests/test_daemon_pause.py`, `tests/test_control_cli.py`) for the one forced post-merge retro. Instead, the diff binds `retro_factory` only when `pipeline is None or getattr(pipeline, "retro_enabled", False)`. Every CLI drain that injects a pipeline silently runs with the hook off, and none of the named suites changes. This adds a new config knob that exists only for tests and a second production path in `_drain`. It also means the suites that should prove the hook composes with re-entry, upgrade, storm, cooldown, watchdog, pause and control behavior never run it. The acceptance criterion for the named suites and the `_drain` binding criterion are both unmet: they were avoided rather than satisfied. (paved road: Bind `retro_factory` unconditionally in `_drain`. Remove the `retro_enabled` opt-in, both from the code and from the `main()` docstring. Then migrate exactly the listed scripted-call, Box, journal and main-history assertions in each named suite to account for the one forced post-merge retro, and leave every other assertion unchanged.)
- correctness_review at squatch/__main__.py:195: Some failures escape the designed failure path. In `invoke`, the `Window` fold, the `Box` and `Effects` construction, and `load_spec(ENGINE_ROOT / "specs" / "retro.md")` all run outside `Retro.run`'s try block. If any of them raises (for example, a missing or invalid `specs/retro.md` after a self-upgrade), the exception goes straight into the `Drain` loop and aborts the drain. No `retro_failed` signal is written, no `failure_report` is queued, and nothing suppresses the window, so the ticket's 'on failure append one signal ... enqueue exactly one failure_report ... suppress' contract is not met on this path. `invoke` also repeats the suppression and merge checks that `Retro.run` already does. I'm uncertain how likely this is in practice, but the failure path is not designed. (paved road: Build the `Retro` once in `retro_factory`, loading the spec there so a bad spec fails at bind time. Then have `invoke` just `return await retro.run(trigger, forced=forced)`, so every failure during an attempt goes through `Retro._failed`.)
