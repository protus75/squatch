## Summary
The files stay inside the fence, but the fixture does not prove what it claims. The 'zero-spend' provider row runs the real `codex` binary, and the scripted CLI returns the wrong verdict for real review prompts. The replay command passes without running the app, and the report fixtures point to replay files that do not exist and state a wrong byte count.

## Findings
- correctness_review at hosts/fixture/config.yaml:6: The provider row `name: codex, kind: cli` is served by the engine's codex adapter, which builds argv `["codex", "exec", ...]` (squatch/providers.py:201). That runs whatever `codex` is on PATH, which is the real billed CLI. Nothing in the profile or tests makes `hosts/fixture/bin/codex` the binary that runs, and that file is mode 100644 so it cannot be executed directly anyway. `est_cost_per_call_usd: 0.0` is only a declared number. The test calls the script with `sys.executable`, which avoids the real path entirely, so the 'zero-spend provider row' criterion is not proven. (paved road: Make the zero-spend path real inside the fence: mark `bin/codex` executable and document or configure how the fixture run puts `hosts/fixture/bin` first on PATH. Then add a test that goes through the engine's provider/adapter path, with the process seam resolving `codex` to the fixture script, and asserts that the real binary is never used.)
- correctness_review at hosts/fixture/bin/codex:9: The script picks the surface from the first of 'author', 'implement', 'review' found anywhere in the prompt. Real engine prompts start with `squatch prompt: surface=<name>`, and a review prompt contains 'implementer', so it would be answered as `implement`. The canned answers also fall outside the engine's closed vocabularies: review returns `"approved"` (the review vocabulary is `approve|snag|rma` and requires `findings`), and author returns `"implemented"`. The test only feeds one-word inputs, so it never sees a realistic prompt. (paved road: Parse the `surface=` token from the prompt's header line and fail closed on unknown surfaces. Return outputs that match each surface's real output contract, e.g. review → `{"verdict": "approve", "summary": ..., "findings": []}`. Test it with prompts that contain the real header and cross-surface words.)
- correctness_review at hosts/fixture/replay.py:18: `replay()` always returns `"result": "pass"` and never calls `app.py`. So the 'deterministic app' is never run, the `fixture-replay` mechanical check can never fail, and `--scenario report-to-regression` does not reproduce the merge-base defect (`classify('Squatch')` → `bird`, expected `animal`). The test's `== ["pass"] * 3` only checks a constant. The acceptance criterion requires the tests to prove the scenarios and the regression. (paved road: Have each scenario run the app and compare its output against recorded expectations. For example, `report-to-regression` should call `app.classify(defect['input'])` and report `actual` vs `expected` from `regression/merge-base-defect.json`. Assert in the test that the regression scenario really reproduces `bird` != `animal`.)
- correctness_review at hosts/fixture/reports/regression-report.json:5: Both reports name `replay_file`s (`replays/regression.json`, `replays/escape.json`) that the diff never creates. Their `replay_bytes` values (256, 512) therefore describe nothing, so the size bound the test asserts is decorative. (paved road: Add the referenced `hosts/fixture/replays/*.json` files. In the test, assert that each file exists and that its real size equals `replay_bytes` and stays under the bound.)
- correctness_review at hosts/fixture/reports/regression-report.json:8: `log_excerpt_bytes` is 48, but the excerpt `merge-base classify('Squatch') returned bird` is 44 bytes. The test only checks `<=`, so the wrong count passes. (paved road: Set `log_excerpt_bytes` to 44 and change the test to `len(report['log_excerpt'].encode()) == report['log_excerpt_bytes']`.)
