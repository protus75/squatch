## Summary
The provider-side event normalization and the kwargs pinning are sound. But the rewritten capture path in SubprocessExec reads stdout with StreamReader.readline(), which has a 64 KiB per-line limit, so every captured call now crashes on long stdout lines. Exceptions other than timeout or cancellation also leave the child's process group running.

## Findings
- correctness_review at squatch/seams.py:133: `_read_stdout` uses `await reader.readline()` on a StreamReader created with the default limit (2**16 bytes). When a single stdout line is longer than 64 KiB, readline raises ValueError ('Separator is not found, and chunk exceed the limit'). The old `proc.communicate()` had no such limit. This path runs for every captured call, with or without a callback. Claude/codex stream-json lines that carry large tool results or file contents routinely exceed 64 KiB, so a call that worked before now raises instead of returning the complete `(rc, out, err)`. That breaks the 'returned capture unchanged' criterion and the ticket's 'changed final capture' reject condition. (paved road: Read stdout in chunks (for example `await reader.read(65536)`), append every chunk to the capture, and split lines yourself from a carried partial buffer. Deliver each complete line, then flush the leftover partial line at EOF. Alternatively pass a sufficiently large `limit=` and handle LimitOverrunError without losing bytes. Add a test_seams case with a line longer than 64 KiB, with and without a callback, asserting the capture is byte-identical.)
- correctness_review at squatch/seams.py:116: The `except` clause only catches `TimeoutError` and `CancelledError`. Before this change, communicate() could only fail with those. The new code adds two more failure sources: an exception raised by `on_stdout_line` (consumer code, which the provider callback forwards into `on_event`) and the readline ValueError above. Either one propagates out of `asyncio.gather` without killing anything. The child's process group keeps running, `err_task` and `proc.wait()` are left pending, and the pipes are never drained. That leaks a running agent process that can keep writing the worktree, which violates the ticket's 'single group-kill-and-wait path' requirement. (paved road: Route every exception that escapes the capture block through `_kill_and_wait` before re-raising, e.g. `except BaseException: await _kill_and_wait(proc); raise`, keeping the existing comment's single-path intent. Or isolate callback failures so they cannot abort capture. Add a test_seams case where the callback raises, asserting the child group is dead afterwards.)
- correctness_review at tests/test_watchdog.py:18: The last acceptance criterion requires test_watchdog.py to prove that no detector, notification, timeout decision, or production callback is activated. The dormancy test only inspects which function and class names are defined in `squatch/watchdog.py`. It never checks that production code (for example `llmeffect.py:63` or `driver.py:128`, which call `CliClient.call` / `LLM.call`) supplies no `on_event`. It also doesn't prove that constructing or using the collector triggers no timeout decision. A later change could wire a production callback while this test stays green. Moderate confidence: the criterion may have intended only module-level dormancy. (paved road: In test_watchdog.py, assert that no production module under `squatch/` other than providers.py references `on_event` / `on_stdout_line` / `EventCollector` (for example an AST or text scan of the package). Alternatively drive the production call path through a fake ProcessExec and assert it received no `on_stdout_line` keyword.)
