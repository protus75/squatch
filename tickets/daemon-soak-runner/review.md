## Summary
The runner drives production Serve and the member fields come from real journals. But the '24 injected hours' is three separate 8-hour serve lifetimes added together. The worker-killed member also reports an 'alert' disposition that no production record backs, and it skips the reconcile-and-re-run the plan requires.

## Findings
- correctness_review at eval/daemon_soak.py: The 24 hours is never experienced by any one production composition. Each member builds its own fresh Serve, and `_InjectedSleep` moves the clock forward only once, by `_HOURS_PER_MEMBER = 8`. `injected_hours` is then measured as max-min of timestamps pooled from three separate journals (`_elapsed_hours`), which gives 24 only because the three 8h jumps add up. No serve lifecycle runs past 8h, and each takes a single sleep, so daily cadences (and most other recurring cycles) never fire. Section 20 exists to require those cycles, and the ticket requires driving the serve composition 'for at least 24 injected hours'. The test's `clock.advances == [timedelta(hours=8)] * 3` and pooled-timestamp assertion lock in this aggregation instead of proving it. (paved road: Advance the injected clock through the serve sleep seam repeatedly, in increments no larger than the shortest recurring cadence, until each member's own serve composition has seen at least 24 injected hours. Compute `injected_hours` from time a single composition actually lived through, not a pooled cross-journal span. In tests/test_daemon_soak_runner.py, assert per member that each daily cadence fired, using that member's journal.)
- correctness_review at eval/daemon_soak.py: The worker_killed_mid_run disposition is made up by the harness. `_entry`'s third branch sets `disposition = "alert"` whenever an accepted kill decision and an `abandoned` transition exist. Neither of those is a Box message or an escalation/alert record. So a fault that lands in silence is still labeled 'alert'. The plan requires every fault to land 'in the box or an alert, none in silence', and the ticket's Definition of rejected rejects self-attested reports. (paved road: Derive `disposition` only from records production writes: a Box message for this run_seq, or a production escalation/alert signal. If neither exists, report the member as not green (or fail the run). Do not infer 'alert' from the kill decision.)
- correctness_review at eval/daemon_soak.py: worker_killed_mid_run does not exercise the closed member section 20 defines: 'a worker killed mid-run reconciled and its stem re-run'. The harness publishes the daemon-lifecycle `kill` (the kill switch, which stops serve). It then opens `runner.session()` so reconcile marks the orphan `abandoned`, and the stem never re-runs. `expected` is set to 'abandoned;kill=accepted', so the member is graded green against a weaker expectation the harness wrote itself. (paved road: Kill the active worker mid-run, then restart the production serve composition on the same state dir so reconcile runs and the stem is re-dispatched. Set `expected`/`observed` from the reconciled terminal plus the new run's terminal, and assert both in tests/test_daemon_soak_runner.py.)
- correctness_review at eval/daemon_soak.py: The conflict members never check the 'main green' part of their definitions. Section 20 requires conflict_resolution_rungs to show both rungs with 'main green after each', and semantic_conflict_integration_red to go integration-red 'WITHOUT main ever going red'. `observed` only reads `strategy_hits`/`rung` or the `gate_failed` finding codes, so a scenario that turned main red would still report green. This is based on the plan text; I could not confirm whether an existing production record carries main health, so this may need plan clarification instead of a code change. (paved road: Derive a main-health component of `observed` from records production writes (for example, the merge queue's post-admission verification on main) for each conflict member, and add it to `expected`. Otherwise, if no such record exists, park the ticket for plan repair instead of dropping the requirement.)
