## Summary
The inbox shape is right and the check report is green, but on replay the consumer applies an existing journaled decision to a request file without checking that it is the same request. A single malformed request file also stops the daemon permanently. The crash-safe publication proof is thin.

## Findings
- correctness_review at squatch/control.py:92: `consume` looks up the journaled decision by `request_id` alone (`decided.get(request.request_id)`) and never checks that `decision.request == request`. `publish` accepts a caller-chosen `request_id` and overwrites the file silently. Example: `publish(request_id="one", action="pause")` is consumed and accepted; later `publish(request_id="one", action="kill", lifecycle="old")` is written. The next `consume` reuses the old `accepted` decision and calls `mutate` with the new kill request. That request was never journaled, never had its lifecycle checked, and gets applied anyway. This breaks decision-before-mutation, identity binding and exactly-once consumption. (paved road: On replay, require `decision.request == request`. If they differ, do not mutate: treat it as a conflict, e.g. journal a distinct refusal outcome and unlink the file. Also make `publish` refuse a `request_id` that already has a pending file or a journaled decision. Add a test for the reused-id case.)
- correctness_review at squatch/control.py:140: `_load` and `_request` raise `ValueError` for any unparseable or invalid file under `control/*.json` (unknown action, extra key, bad JSON). `consume` does not handle it, so every pass fails on the same file and later requests are never consumed. Under `DaemonTasks` a callback exception shuts the daemon down, and on restart it fails again on the same file. One malformed request permanently stops the control path and the daemon, with no designed release. That breaks the fail-closed-with-paved-road rule. (paved road: Handle an invalid request file as a designed outcome. Journal an `invalid` decision keyed by the file name (the journal remains the only writer), then unlink or quarantine the file and continue the pass. Add a test in `tests/test_control.py` showing that a malformed file does not block a valid request behind it.)
- correctness_review at tests/test_control.py:21: The first acceptance criterion asks `tests/test_control.py` to prove crash-safe publication, and the scope asks it to prove replay at crash points. The test named `test_publication_is_atomic...` only checks the file's final contents after a successful `publish`. It never simulates a crash during publication, e.g. a leftover `.<id>.json.tmp` partial file, and never asserts that such a file is ignored by `consume`. The only crash point exercised is an exception inside `mutate`. Uncertain whether reviewers accept relying on `LocalFilesystem.write`'s atomicity without a test here, so this is flagged conservatively. (paved road: Add a test that leaves a partial temp file in `control/` (the name `LocalFilesystem.write` uses), or injects a Filesystem fake that fails before the rename. Assert that `consume` ignores it and later consumes the completed request exactly once.)
