## Summary
Fence, wiring and checks are clean, but the exactly-once and crash-replay guarantees are incomplete: a crash window can apply a mutation twice, an accepted request can be dropped without a journal record, a mis-scoped exception deletes valid requests, and two acceptance proofs are only nominal.

## Findings
- correctness_review at squatch/control.py:101: Consumption is not exactly-once. `await mutate(request)` runs before the `applied` signal is appended. A crash between the two leaves an `accepted` decision with no `applied` record, so replay in the same lifecycle calls `mutate` again. The only crash test (`test_crash_after_mutation_replay_is_not_a_second_mutation`) crashes at the final `unlink`, after `applied` is already journaled. It never exercises this window or the one between decision and mutation, so the ticket's 'prove replay at crash points' is met for only one point. Uncertainty: if the design intends mutations to be idempotent, that contract is neither stated nor tested. (paved road: Make the journaled decision the only commit point and state that `mutate` must be idempotent, or record application atomically with the mutation. Add tests that inject a crash (a) after the decision append and before `mutate`, and (b) after `mutate` and before the `applied` append. Each test must assert the mutation count after replay.)
- correctness_review at squatch/control.py:87: An accepted-but-unapplied request is dropped without a journal record. If the journal holds an `accepted` decision from an earlier lifecycle, `_decision` returns that existing decision. The `request.lifecycle != self.lifecycle` branch then deletes the file and returns an in-memory `stale` outcome that is never journaled. The journal permanently shows the request as accepted with no `applied` and no terminal outcome, so the record disagrees with what happened. (paved road: Journal a terminal outcome (e.g. a `stale` signal keyed to the request_id) before deleting the file. Add a test for a restart after an accepted decision, before application, that asserts the journaled outcome.)
- correctness_review at squatch/control.py:78: The exception is caught too broadly. `except Exception` covers `path.read_bytes()` as well as validation, so a transient OSError on read is classed as `invalid` and the file is deleted. A valid durable request is lost. If the file has already vanished, the following `unlink` also raises an unrelated error from inside the handler. (paved road: Read the bytes outside the try block and catch only `pydantic.ValidationError` (plus `ValueError` for malformed JSON) around `model_validate_json`. Let OSError propagate so the file stays in place for the next pass.)
- correctness_review at tests/test_control.py:84: `test_interrupted_publication_leaves_no_request_to_consume` does not prove crash-safe publication. Its `Interrupted` subclass replaces `publish` entirely, so the real `LocalFilesystem.publish` (temp write, fsync, link, directory fsync, cleanup) never runs. The test's temp-file name also differs from the real `.{name}.{uuid}.tmp` form. The only real-code test (`test_seams.py`) covers just the no-overwrite path. No test shows that a failure during the real write or link leaves no target and no temp file. (paved road: Test the real `LocalFilesystem.publish` by injecting a failure inside it, e.g. monkeypatch `os.link` or `os.fsync` to raise. Assert that the target does not exist, that no `.tmp` remains, and that a later `consume` finds nothing.)
- correctness_review at tests/test_control.py:55: Restart identity is not proven. Every test passes an explicit `lifecycle=` and runs in one Journal and inbox. No test builds two inboxes with the default lifecycle and checks that their identities differ, and none reopens the journal over the same state_dir to replay across a real restart. The first acceptance criterion ('restart identity') is therefore met only by assertion in the docstring. (paved road: Add a test that closes the Journal, reopens it on the same `tmp_path`, and builds a new `ControlInbox` without passing `lifecycle`. Assert that its lifecycle differs from the first inbox's, and that a request addressed to the earlier lifecycle is decided `stale` and never mutates.)
