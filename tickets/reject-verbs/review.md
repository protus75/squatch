## Summary
The verbs, cap fold bound, premise_bounce draw, and drain wiring mostly match the ticket. Three things still block merge: both verbs accept a stem that is already `rejected`, the spent-premise road can name the wrong cap, and one drain acceptance test is in the wrong file.

## Findings
- correctness_review at squatch/runner.py:204: `Runner.reject` does not refuse a stem whose latest transition is already `rejected`. On a second `squatch reject <stem>` it journals another `reject` signal and another `to: rejected` transition, then calls `commit_lane` with `stamp(text, state="rejected")`. Those bytes match the committed file, so the pathspec `git commit` has nothing to commit and fails with the two journal events already written: a partial write that ends in a crash. If the commit did succeed, it would also file duplicate `dead_dependency` signals and duplicate box `failure_report` messages for every dependent. (paved road: Before any write, refuse a stem whose latest `state_transition` is `rejected`, the same way a merged stem is refused (for example, extend `_not_merged` to a terminal-verdict check over `merged` and `rejected`), and add a test that a second `reject` exits 2 and writes nothing.)
- correctness_review at squatch/runner.py:191: `Runner.confirm` on a `rejected` stem goes down the keep path. It journals an operator `confirm` signal and reports `confirmed: <stem> re-enqueued` with exit 0. But `Drain._scan` skips every stem whose latest transition is `rejected`, so nothing is re-enqueued: the verb claims an action it did not take, and the signal also resets that stem's cap fold. I'm treating this as a defect even though the ticket only spells out the merged refusal, because the report claims a re-enqueue that cannot happen. (paved road: Refuse `confirm` on a `rejected` stem (a kill is terminal, like merged), and cover it in tests/test_verbs.py.)
- correctness_review at squatch/drain.py:367: The premise-park road uses `spent(...)`, which returns the first spent cap of any spine cap (retry, diagnosis, premise_bounce, infra). `_released` checks only `remaining(..., PREMISE_BOUNCE_CAP)`. So a `premise_failed` stem with a spent retry cap but premise_bounce budget left is released by a ticket edit alone. Its parked line still says `retry cap spent ...; edit the ticket as required, then squatch confirm` and names the wrong cap and the wrong release. The ticket requires the parked line to name the spent `premise_bounce` cap. (paved road: Choose the premise road from the premise_bounce cap alone. When `remaining(config, cap_drawn, stem, PREMISE_BOUNCE_CAP) == 0`, build the reason `premise_bounce cap spent (<drawn> of <budget> drawn)` and the confirm road; otherwise fall back to `_premise_road`. This matches the predicate `_released` uses.)
- correctness_review at tests/test_drain.py: One acceptance criterion requires tests/test_drain.py to cover this case: a `premise_failed` stem under `caps: {premise_bounce: 1}` with one draw is not released by a ticket edit alone, its parked line contains `premise_bounce cap spent (1 of 1 drawn)` and `squatch confirm`, and it runs in the next drain after `squatch confirm <stem>`.
