## Summary
The intake, custody and serve wiring are mostly sound, but four things need fixing. Bug reports that triage marks as tombstone or decision now stay pending forever. A configured inbox makes triage run and append a journal signal on every poll. Two inbox tests do not prove the ordering and excerpt-cap criteria they claim. Report metadata files are read with no size limit and are never drained.

## Findings
- correctness_review at squatch/triage.py:231: The new guard `message.message_class == "bug_report" and getattr(verdict, "kind", None) != "bug"` catches every non-author verdict. TriageTombstone and TriageDecision have no `kind`, so any bug report that triage correctly tombstones as a duplicate or turns into a decision is skipped instead of going to `_apply`. It stays pending forever and is re-triaged, with a fresh LLM call, on every pass. That is a hold with no release path. (paved road: Apply the kind check only to authoring, e.g. `if isinstance(verdict, TriageAuthor) and message.message_class == "bug_report" and verdict.kind != "bug"`. Let tombstone and decision verdicts reach `_apply`. Add a test showing a tombstoned bug_report gets resolved.)
- correctness_review at squatch/serve.py:135: When `inbox` is set, `box()` calls `inbox_consumer` on every poll, and that always awaits `triage.run`. The old `pending()` gate is gone on this path. `Triage.run` does a git rev_parse, builds a driver, and always appends a `triage_pass` signal to the journal, even when nothing is pending. With an idle inbox configured, the journal gets one record every POLL_SECONDS forever. The journal is the record, not a debug log. (paved road: Consume the inbox first, then run triage only if `triage.box.pending()` is non-empty. Either gate inside `inbox_consumer`, or call `inbox.consume()` and then keep the existing `if triage.box.pending(): await box_consumer(...)` branch. The serve test still covers the case where Box starts empty, because the report is ingested before the pending check.)
- correctness_review at tests/test_inbox.py:28: Acceptance criteria 1 and 2 are not really proven. `test_invalid_metadata_is_rejected_before_replay_read` creates no replay file, so the report would be rejected (unreadable replay) even if the replay were read before metadata validation; the test cannot tell the two orders apart. In `test_actual_replay_and_excerpt_caps_precede_box_recording`, the excerpt report points at the same oversize `replay.json`, so it would be rejected by the replay cap even if the 64 KiB excerpt cap were removed. (paved road: For ordering, give a bad-metadata report a valid replay file and assert the replay was never read, e.g. with a spy Filesystem that records `read` calls, or a replay path that raises if touched. For the excerpt cap, point the oversized-excerpt report at its own valid small replay file so the excerpt cap is the only reason for rejection.)
- correctness_review at squatch/inbox.py:124: I'm less sure this one is in scope. `_metadata` reads the whole `*.report.json` into memory with no byte limit before validation. The 64 KiB excerpt cap only applies after parsing, so a huge report file is loaded in full on every poll. Also, successfully consumed reports are never moved or removed, so every poll re-reads and re-parses every past report forever, which only the `by_origin` duplicate check short-circuits. The ticket says not to retain unbounded evidence. (paved road: Before reading a report file, check its size against a fixed limit (about LOG_EXCERPT_LIMIT plus metadata headroom) and reject anything larger. After a successful enqueue or a duplicate match, move the report out of the scan glob (e.g. rename to `.filed`), the same way rejected reports are renamed to `.rejected`.)
