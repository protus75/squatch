## Summary
The hold logic is mostly sound, but the production drain now has two consumers on one control inbox. DispatchPause's consumer can take a matching release and delete it, so the admission hold never clears. The inbox sharing is order-dependent, uses a raw sleep, and several required test proofs are missing.

## Findings
- correctness_review at squatch/mergequeue.py:113: AdmissionHold.wait() runs its own `inbox.consume(self.apply)` loop, so it becomes a second consumer of the same inbox that the drain's `wait_for_control` consumes with `pause.apply` (squatch/__main__.py _control_factory). ControlInbox._consume accepts a release whose hold_id is in `inbox._holds`, and `_trigger` puts it there through `inbox.hold`. If the drain boundary consumes that release first, it calls `discard_hold`, then `DispatchPause.apply`, then deletes the file. `AdmissionHold.apply` never runs, `_hold_id` stays set, and admission waits forever. A matching resume can therefore be silently lost, which breaks 'matching resume releases exactly the owning hold' and 'reaches the hold through the one consumer'. (paved road: Do not consume inside AdmissionHold. Wire `hold.apply` into the single production consumer in `_control_factory`, for example with a composite mutation that calls `pause.apply` and then `hold.apply`. Have `wait()` wait on an asyncio.Event that `apply` sets.)
- correctness_review at squatch/__main__.py:290: Inbox sharing depends on call order and a function-attribute side channel (`setattr(config_supplier, '_inboxes', ...)`, keyed by `id(journal)`). If the Runner calls the pipeline factory before the Drain's control factory for a journal, `inbox_for` builds a second holder-less inbox with its own lifecycle record. `_control_factory` then overwrites the dict entry with a third inbox, so two inboxes exist for one journal. The ticket forbids this ('never construct or race a second inbox'). `inbox_for` is also effectively a fallback path that constructs its own inbox. Keying on `id()` is fragile because ids can be reused after garbage collection. (paved road: Create the one lock-held inbox once per journal in a single place and pass it explicitly to both the control factory and the pipeline factory, for example by building both from a shared per-journal composition function. Remove the setattr side channel and the lazy second-construction path.)
- correctness_review at squatch/mergequeue.py:116: `wait()` calls raw `asyncio.sleep(1)` in engine code, which bypasses the injectable clock/sleep seam. It also polls, although the ticket asks for a hold that waits without busy-polling. (paved road: Block on an asyncio.Event set by `apply`, which the single control consumer drives. If a delay is ever needed, inject the sleep seam.)
- correctness_review at tests/test_daemon_composition.py:228: Acceptance criterion not met. The only change here passes a fresh `compose_daemon_control` inbox to an existing test. No test proves that the lock holder shares one inbox between dispatch pause and the production merge admission hold, or that a matching resume reaches the hold through the one consumer. That missing proof would have caught the double-consumer defect. (paved road: Add a test that drives the `__main__` drain composition (or `_control_factory` plus the pipeline factory) over one journal. It should assert that the pause and the queue's `admission_hold` share the same inbox object. It should also publish a matching release and consume it through `wait_for_control`, then assert the admission hold clears.)
- correctness_review at tests/test_mergequeue.py:96: Acceptance criteria only partly met. The new tests call AdmissionHold methods directly. Nothing proves that rebase or regate failures do not count toward the streak, that green resets the streak through the queue, or that another task progresses while admission waits.
