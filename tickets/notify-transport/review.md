## Summary
The seam, config, Effect keys and Serve wiring are sound, and provider keys are stripped from the notification env. The reconciler has three defects: it re-prints every delivered escalation on every poll, a notifier timeout escapes and crashes serve, and the storm-trip resume action is a literal placeholder rather than a usable command. The unset-config test also does not prove that no transport call happens.

## Findings
- correctness_review at squatch/notify.py:37: When a key is already completed, Effects.run returns the cached result without calling deliver, but the `else` branch still runs `self._report(rendered)`. Serve calls reconcile at startup and on every watcher poll, so every escalation delivered in the past is printed to the daemon output again on every poll, forever. The daemon's report stream becomes an unbounded repeat of old escalations. (paved road: Report only when delivery actually happened. For example, set a flag inside `deliver()` and report only when it is set, or check `key in self._effects._completed` before the run. Add a test where a second reconcile over completed keys produces no report lines.)
- correctness_review at squatch/notify.py:34: SubprocessNotifications passes timeout=30.0 to SubprocessExec.run, which re-raises TimeoutError after killing the process group. The reconciler catches only (ExecutableNotFound, RuntimeError). A hanging notification command therefore raises out of reconcile. At startup this aborts Serve.run before dispatch; on a poll it fails the watcher callback. The ticket requires that notification failures be reported through the status path and never break the daemon. (paved road: Catch TimeoutError in the reconciler, or turn a timeout into the wrapper's declared failure (for example, a RuntimeError raised from SubprocessNotifications.notify). Add a test_seams or test_notify case with a notifier that times out.)
- correctness_review at squatch/notify.py:47: The storm-trip escalation renders the literal text `resume: squatch resume --hold-id <storm-trip-hold-id>`. `squatch resume --hold-id` takes a UUID (`__main__.py` line 83), so the operator gets a command that cannot run. The real release id is the hold_id on the `control_hold` signal with trigger `storm_trip` and a matching trip_id, which daemon.py journals. The ticket requires rendering the escalation's pull-side `resume` action, and a placeholder does not satisfy that. (paved road: Render the real hold id. Either drive the storm-trip notification from the materialized `control_hold` (trigger `storm_trip`, keyed on trip_id, which is still durable), or look up the matching hold for the trip_id. If no hold has been materialized yet, render the escalation without a fabricated command, and cover the rendered resume line with a test.)
- correctness_review at tests/test_serve.py:86: The acceptance criteria require proof that an unset config.notify gives status-only behavior with no transport call. test_unset_notification_config_warns_once_and_stays_status_only checks only the warning count and that callbacks exist. It never substitutes a recording notification transport and never asserts zero calls, and the journal it uses holds no escalation signal to exercise the path. (paved road: In that test, monkeypatch `main_module.SubprocessNotifications` with a recorder, seed a storm_trip or integration_red_streak signal, run a watcher poll callback, and assert the recorder was never called and no reconciler was built.)
