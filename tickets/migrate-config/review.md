## Summary
The core 0-to-1 scalar substitution, the loader validation and the single-verb wiring are sound. The backup step can destroy an existing file and can leave a write behind when migrate-config refuses, and the CLI tests do not cover the no-write boundaries the acceptance criteria require.

## Findings
- correctness_review at squatch/config.py:357: `fs.write(backup, ...)` uses the seam's replace-over-destination write, so an existing `config.yaml.bak` is silently overwritten. If the host already keeps a file with that name, or a backup is left from an earlier failed attempt, those bytes are destroyed. That is a lossy write to a path the host owns, and the backup can no longer be trusted to be the only copy of the original. (paved road: Publish the backup with `fs.publish` (it refuses to replace an existing path) and turn a FileExistsError into a ConfigError that tells the operator to move the existing backup aside. Add a test in tests/test_config.py where a pre-existing `.bak` makes migrate refuse, with both files unchanged.)
- correctness_review at squatch/config.py:360: If the temporary write or the replace fails with an OSError, the backup has already been written. The handler removes only the temporary file and raises ConfigError, which the CLI reports as a refusal, so a refusal leaves a new file on disk. The ticket's Definition of rejected lists 'a write on refusal'. The same OSError path is also untested. A related but separate gap: `fs.read(path).decode()` raises an uncaught UnicodeDecodeError on non-UTF-8 input, so that input bypasses the designed ConfigError/Refusal path. I am not certain the harness handles that exception safely. (paved road: In the OSError handler, also remove the backup, but only if this call created it, which the `publish` change above guarantees. Catch UnicodeDecodeError on read and raise it as a ConfigError. Add a test using a fake Filesystem whose `replace` raises, and assert that neither the backup nor the temporary file remains and that the config is unchanged.)
- correctness_review at tests/test_cli.py:242: Acceptance criterion 3 requires tests/test_cli.py and tests/test_verbs.py to prove ALL no-write boundaries. The CLI refusal test covers only two cases: an unknown key and version 2. At the CLI level there is no case for a missing version, a non-integer version, a negative version, input that is invalid only after substitution, or an unreadable (missing) config file. There is also no CLI test that a current version-1 config is a no-write, byte-identical `current` result. And test_verbs only asserts that `migrate-config` is in a superset (`<=`), which does not show it is the sole new verb. (paved road: Extend the parametrized CLI refusal test to cover `schema_version` absent, `"0"`, `-1`, `2`, an unknown key, and a version-0 document that is invalid after substitution (for example `notify: null`), plus a missing config.yaml. Assert rc == EXIT_REFUSED and that neither the config nor the `.bak` file changed. Add a CLI test that a version-1 config prints `migrate-config: current` and stays byte-identical with no `.bak`. In test_verbs, assert the exact expected verb set so that any extra verb fails the test.)
