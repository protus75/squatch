No ticket. The behaviour described is real. Every child process gets the engine's own environment minus provider keys (`child_env`, squatch/providers.py:378-381). The verification gate runs each `## Verification` argv with `cwd=workspace`, the ticket worktree (squatch/stages.py:376, :405 for the base re-run, :534/:557 for regression). Nothing sets `UV_PROJECT_ENVIRONMENT`, so `uv run pytest` in a fresh worktree resolves that worktree's own project and builds a `.venv` there. The default ticket template (squatch/tickets.py:884-889) makes `uv run pytest` the standard Verification command, and the plan uses it everywhere. The message itself says this is an operator or ticket-authoring note and not an engine defect. It cites no incident (`evidence: None`), and nothing so far shows harm. Phases 2 through 6 all merged with this command. uv's shared cache hardlinks packages, so the per-worktree venv costs some time and some disk, and it goes away when the worktree is removed. Neither fix suggested is free. Injecting `UV_PROJECT_ENVIRONMENT` into the verification env would point the branch's tests at the checkout's installed environment, so a ticket that changes dependencies in `pyproject.toml` would be verified against main's dependencies, not its own. That weakens the branch-isolation property the gate depends on, and the base-diff re-run at the merge base has the same problem. Naming the checkout's interpreter in Verification commands has the same flaw and also ties tickets to the host's path layout. With no measured cost, either change is a speculative knob under the build-the-simplest-thing rule (D10). No rendered work or decision covers where the verification venv lives. verification-attribution covers base-diff attribution, not the environment, and startup-interpreter-floor covers only the Python version floor. A tombstone would therefore be wrong. Reopen if a soak, status or engine-log measurement shows per-worktree venv creation is a large share of Check or merge-admission time, if disk use under the worktree root becomes a problem, if a verification run fails or times out because of venv creation, or if a regeneration changes the default Verification command or the verification child env.

Evidence: squatch/providers.py:378-381 (child_env passes the environment through minus provider keys, with no uv variables set). squatch/stages.py:376, :405, :534, :557 (verification and regression commands run with cwd set to the ticket worktree or the base worktree, using the child env). squatch/tickets.py:884-889 (the default ticket template's Verification is `uv run pytest`). The message has `evidence: None`. Merged phase2-exit through phase6-exit ran with this behaviour and no incident was recorded.
