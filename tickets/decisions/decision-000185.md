No ticket. The message is accurate, and it says itself that the cost does not matter at the current scale. `Drain._scan` (squatch/drain.py:298-326) still runs on every pass of the `_drain` loop (drain.py:230-231). Each pass calls `pending_stems` (one git status) and re-lints every committed, unmerged, non-rejected stem from disk before choosing the next offer. This re-scan is deliberate: it is how the bootstrap drain sees ticket files that a merged seeding run lifted, or that were edited, within the same invocation. It is also how a stem that no longer lints, or whose stuck budget is over the limit, gets held with a paved road. Caching the scan would add a second freshness path and a way for the drain to dispatch from a stale plane. The no-dual-path and simplest-thing rules both weigh against that. The replacement the message names is already merged. scheduler-activation and daemon-scheduler delivered the watcher-driven priority snapshot for the production serve composition. The re-scan therefore stays only on the bootstrap `drain` verb, which by design runs at self-build scale. Each dispatch is a full implement/check/review/merge pipeline of LLM calls, so one git status and a few dozen YAML lints per dispatch are negligible. The message gives no evidence of measured latency or cost (evidence: None), so under D10 an optimization ticket would be speculative. A tombstone does not fit. scheduler-activation covers the watcher in serve, not a change to the bootstrap drain's scan, and no open ticket or decision covers scan cost. Reopen if the drain's pre-dispatch scan is measured as a meaningful share of wall-clock or provider-idle time per dispatch, if a host plane's committed unmerged ticket count reaches the hundreds, or if the plan moves bulk host draining off `serve` and onto the bootstrap `drain` verb.
