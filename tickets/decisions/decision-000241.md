Plan section 12 (SQUATCH_PLAN.md:1186) says class-specific triage prompting lives inside the single `specs/triage.md`, and that the one spec renders a per-class Task variant keyed by the message class, never a spec file per class. Its binding rule is section 8's one-file-per-surface law, and the shipped code meets it. There is one `specs/triage.md` surface (consumed at squatch/triage.py:144). Its one Task section lists all five variants (`suggestion`, `failure_report`, `override_report`, `retro_finding`, `bug_report`), and the model picks one using the `message_class` field in the rendered message block. No spec file exists per class. This same render is producing working verdicts in the live triage pass, as the run of decision and tombstone records in the registry shows. Adding a conditional directive to `Spec.render` in squatch/specs.py would put a second render mechanism next to the plain data-directive grammar for a single consumer. The only gain would be a few hundred bytes per render. Nothing shows that inline selection has misrouted a message. The message gives no evidence and comes from bootstrap-ingest, so under D10 the directive would be a speculative feature. If 'renders' is read as engine-side selection, that is a wording gap and not a behavior defect, and it does not justify regenerating merged code. A tombstone does not fit, because no rendered ticket Goal or decision covers how triage selects its per-class variant. Reopen if a triage verdict is shown to have applied the wrong class variant (for example a `failure_report` handled under the `suggestion` rules), if the triage render gets close to its size bound because of the inline variants, or if section 8 or 12 is edited for another reason and the wording can be made exact at no extra cost.
