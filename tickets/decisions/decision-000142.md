No ticket. This is a bootstrap-era design note, not new work. Its facts are still true: specs/implement.md:7 declares `gates: []`, so the Driver's in-stage gate pass (squatch/driver.py:155-162) runs nothing for Implement. The mechanical gates run once at Check (squatch/stages.py:943), and a hard failure there ends the run `gate_failed` (stages.py:708). Verification runs again at merge admission (squatch/merge.py:386). The trade-off the note records is deliberate: putting the gates on the implement spec would add a third verification run to every admission, and no incident has earned it (`evidence: None`). Under the build-the-simplest-thing rule (D10), that makes it speculative. One part of the note is out of date. It describes the Phase 1 cost of a red Check as exit 1 with the branch torn down on re-entry. That cost is now lower: spine-harvest, spine-diagnosis and spine-caps (merged) harvest the red attempt, attach diagnosed lessons, and re-offer the stem under the `retry` cap. Today a run-record slip at Check costs one retry draw, not a stranded ticket. No rendered work or decision covers where the mechanical gates sit or whether Implement carries an in-stage gate list. The gate-related drafts (gates-lint-before-run, gate-finding-code-lint, gates-crash-continue-cancel-pin) only touch `run_gates` internals. A tombstone would therefore be wrong. Reopen if a real ticket spends a `retry` draw (or exhausts `retry`) only because of a run-record or other mechanical-gate slip that an in-stage re-prompt would have fixed, if a regeneration adds gates to specs/implement.md, or if Check stops running the four mechanical gates.
