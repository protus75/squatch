No ticket for now. The gap is real: section 6 says per-provider concurrency caps are enforced by the dispatcher before the call, and that cap-wait time is journaled and excluded from the watchdog's wall-clock regions. In the code, though, `squatch/thresh.py` (`ThresholdRuntime`, from the merged `thresh-runtime`) is imported by no production module, and `squatch/watchdog.py:254` says Stages has no provider-cap wait in its call path, so the detector gets no wait observations. Even so, the message names no incident. It cites no run that hit a provider-side concurrency rejection, and no watchdog trip caused by an unrecorded cap wait. Under D10, an addition has to cite the incident that earned it. The current dispatcher is the single-flight scheduler (`daemon-scheduler`, `dispatch-admission-boundary`), so a ticket's stage calls run one at a time and a cap wait is unlikely to show up as watchdog spend. Wiring an admission owner into every provider call path is also a cross-cutting activation that no phase registry in the plan lists. The plan is the seed, so this activation should be added as a plan registry item before any ticket is authored, not written as an ad-hoc box ticket. A tombstone does not fit: no rendered open work, merged Goal or decision covers activating `ThresholdRuntime`. decision-000266 covers watchdog binding for other roots, not cap-wait supply. Reopen if any run records a provider-side concurrency or rate rejection that a pre-call cap would have stopped, if a watchdog trip is traced to time spent waiting on a provider, if dispatch stops being single-flight, or if the plan adds a threshold-runtime activation item.
