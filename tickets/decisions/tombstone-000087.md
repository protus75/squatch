The open draft ticket journal-fsync-fail-closed already covers the gap this message names: how the process reacts when a fault happens inside the journal's write path. Its scope is `Journal.append` raising from the line write, `flush`, or `os.fsync`. In each case the instance marks itself broken, re-raises the original exception, and refuses every later append. Its regression test (`tests/test_journal.py::test_append_fsync_failure_fails_closed`) injects the fault by monkeypatching `os.fsync` to raise once. It then checks the in-process reaction (the broken instance, the dedup refusal in `Effects.run`, the immediate refusal of an unrelated append) and the replay from disk by a fresh instance. A short write raises from the same line-write path, so the same broken-instance handling covers it. The ticket deliberately puts 'any new fault-injection seam or harness fault point' out of scope, and its stop condition throws the branch away if a seam is needed. So the open work already rules on the seam the message proposes: monkeypatching `os.fsync` is enough to inject the fault, and the anti-bloat law forbids a dedicated filesystem seam for the journal until an incident shows that monkeypatching cannot reach a fault. The on-disk side is already covered by the byte-offset sweep in tests/test_fault_injection.py, as the message says. Reopen if journal-fsync-fail-closed is rejected or merges without the in-process test, or if a write-path fault (for example a partial `write` that returns without raising) is found that `os.fsync`/`write` monkeypatching cannot reproduce. In that case, author a narrowly scoped seam ticket for the journal's append path.
