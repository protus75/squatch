No ticket. The behavior is real, and the code is strict on purpose. `Stages._prior_attempts` (squatch/stages.py:840-842) parses `tickets/<stem>/checks.json` with `Invoice.model_validate_json` and does not catch a parse failure. A malformed file therefore raises out of the Implement render. It parses the harvested `attempts/<n>/harvest.json` files the same strict way (stages.py:864-865 and 896-897). All of these are engine-written artifacts on the ticket plane, and only the one ticket-plane lift path produces them. A file that fails to parse means either a hand edit outside the sanctioned paths or an engine defect, and the message itself argues that stopping is the right response to an engine defect. The engine handles its other engine-owned records the same way: corrupt journal records and box records are refused, never skipped (journal corruption-strict, section 6). Making only `checks.json` soft would give one family of artifacts two parse policies, since harvest.json would still raise. If every one of them were softened, a corrupted record would quietly drop out of the lessons the next attempt is fed. That would cost visibility in order to keep the queue moving, and the no-dual-path and fail-closed rules both weigh against it. The 'harvest is soft' idea the message cites is about extracting from a dying worktree (section 11.2), not about reading back artifacts the engine already committed. There is also no evidence (evidence: None). No journal shows a stem stalled on an unparseable checks.json, and the `bootstrap-ingest` origin dates the message to before the current Invoice schema was settled. Under D10 the change is speculative. A tombstone does not fit: drain-parked-detail only says where checks.json is listed in the report, not how it is parsed, and no rendered decision covers re-entry parse strictness.

Evidence: squatch/stages.py:840-846 (strict Invoice.model_validate_json on checks.json); stages.py:864-865 and 896-897 (the same strictness for harvest.json); the message's own note that it was left strict on purpose; message evidence: None. Reopen if a journal shows a stem faulting repeatedly at the Implement render on an unparseable checks.json or harvest.json, if a schema migration leaves older-schema checks.json files on main, or if the plan adds a soft-read rule for re-entry artifacts.
