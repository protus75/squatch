No ticket. The message says the two key parts always have the same value in v1. That is only true for ticketed stages. The plan's 'one attempt per run entry' sentence (SQUATCH_PLAN.md:1016) is about the per-ticket spool and harvest directory, `<state_dir>/spools/<stem>/<attempt>/`. On ticketed stages the stage layer passes `attempt=run_seq` (squatch/stages.py:1028, squatch/rework.py:179), so there the two parts are equal. The same `llm_key(stem, run_seq, surface, attempt, call_seq)` (squatch/llmeffect.py:31) also serves the ticket-less surfaces. On those, the Driver spools under the surface name (squatch/driver.py:113), and the two parts carry different counters. Triage passes run_seq=message.seq, attempt=pass_number (squatch/triage.py:225). Author passes run_seq=pass_number, attempt=message.seq (squatch/author.py:175). Retro passes run_seq=window.sequence+1, attempt=0 (squatch/retro.py:291). Dropping either part would mix up message identity and pass identity on those surfaces, which could make two different calls share a replay key. That is a correctness risk, not a cleanup. The Phase 1 deliverable text (SQUATCH_PLAN.md:1467) names the five-part key, and the merged code matches it, so plan and code agree. What remains is optional plan wording: section 6 could say that on ticket-less surfaces `attempt` is a separate counter, not the run sequence. Engine tickets cannot change plan prose, so this goes to the operator, as decisions -000102 to -000105 did. Smaller optional point for the operator: triage and author put message.seq and pass_number in opposite slots. Both orders give unique keys, so nothing is broken. No open or merged work or decision covers the shape of the LLM effect key, so a tombstone would be wrong. Reopen if a regeneration drops either key part, if ticketed stages start passing an attempt different from run_seq, or if the operator rewrites the section 6 attempt wording.
