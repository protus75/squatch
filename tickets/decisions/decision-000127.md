No ticket. The code fact is correct, but the cost only applies to work that rarely exists, and no incident shows it causing harm. `Intake._predecessor_source` (squatch/tickets.py:686-693) reads every event through `self._journal.read()` each time it is called. `_human_stamps` (:699) calls it once for each pending stem that gets past the frontmatter parse in `Intake.run` (:741). The watcher the message is waiting for has already merged (scheduler-activation, serve-activation): the production `priority_snapshot` (squatch/serve.py:247-262) builds a fresh `Intake` and awaits `intake.run()` on every cycle. So the cost is live today, but it scales with the number of pending stems, not with the cycle. `pending` only covers hand-authored ticket files on the ticket plane that are not yet committed, and in steady state that is zero, so the per-stem scan never runs. The same cycle already reads the whole journal once for `fold(journal.read())` (:254), so even one pending stem only adds one more read of the same size. The merged daemon-soak and soak-run reports exercised this composition and found no cycle-latency problem. Building a per-cycle intake-signal map now would be a speculative optimisation with no incident behind it, which the build-the-simplest-thing rule forbids. No rendered work or decision covers how intake reads the journal. decision-000122 and decision-000123 cover `Depends on` resolution and the uncommitted-neighbour resolver in the same `Intake`, not the cost of the source-stamp lookup. scheduler-activation and serve-activation built the watcher but say nothing about this cost. A tombstone would therefore be wrong. Reopen if a soak, status, or engine-log measurement shows `Intake.run` taking a large share of watcher-cycle time, if a bulk hand-authored intake (many pending stems at once) stalls a cycle, or if journal growth makes one full read per cycle expensive.
