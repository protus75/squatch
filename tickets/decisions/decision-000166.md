No ticket. The facts in the message are correct, but the behavior it describes is the one the plan specifies, and the message itself says it is right for a missing binary. In `Driver` (squatch/driver.py:133-137), `ExecutableNotFound` is re-raised on purpose. The comment there cites sections 11.1 and 15: a missing binary means no call ran, so it is a config/setup defect, and turning it into an `infra_error` would draw the infra cap for a fault that more capability cannot fix. `Runner._fault` (squatch/runner.py:502-504) turns it into a `Refusal` whose paved road says to install the binary or fix the provider `cli` entry. It leaves the run `running` for reconcile, and under drain that refusal stops the queue (section 18). The message suggests that per-provider unavailability should park instead, using the drought machinery. That machinery is already merged (thresh-runtime, provider-cooldown-failover, and `provider_hold` in squatch/__main__.py:567-586, which journals a `provider_drought` signal). But section 6 (SQUATCH_PLAN.md:1088) defines a drought narrowly: a resolved tier whose candidates are all unavailable because of an open breaker, a cooling quota, or an exhausted tier. That is weather, which resolves with time. A misconfigured binary never resolves with time. If it parked as a drought, every routed stem would sit cost-free and silent until the fleet-wide drought escalation fired, and the operator would get a weaker signal than today's immediate refusal, which names the exact binary. A drought is released when routing resolves again, and nothing can resolve a missing executable automatically. So under the 'a hold ships with its release' rule, such a park would have no machine release. Reclassifying ExecutableNotFound as a drought would change section 6/11.1 semantics, so the plan would have to change first, and that is the operator's call. The message also cites no evidence, and Phases 3-6 merged without hitting this. No rendered work or decision covers whether a missing provider binary should refuse or park. provider-cooldown-failover and thresh-runtime cover only classified cooldowns and breaker state, so a tombstone would be wrong. Optional operator action: if a multi-provider fleet should keep draining when one provider's binary is missing, state in section 6 that a provider whose `cli` binary does not resolve counts as an unavailable candidate (with failover to the next configured candidate and a named escalation), then regenerate driver.py/providers.py. Reopen if a journal or engine log shows a drain stopped by a missing provider binary while another configured candidate for the same tier and surface could have served it, or if the operator changes section 6 as described.

Evidence: squatch/driver.py:133-137 deliberately re-raises ExecutableNotFound as a setup refusal (sections 11.1, 15). squatch/runner.py:502-504 refuses with the paved road 'install it, or fix the provider `cli` entry'. SQUATCH_PLAN.md:1088 limits drought to unavailable candidates (open breaker, cooling quota, exhausted tier), a routing outcome released when routing resolves again. squatch/__main__.py:567-586 provider_hold journals provider_drought only for ProviderError from providers.resolve. The message has evidence: None and concedes the current behavior is right for a missing binary.
