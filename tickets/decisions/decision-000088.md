No action now. The message describes the harness correctly, but the gap is latent: nothing on today's crash path behaves differently when the process unwinds instead of dying. In tests/test_fault_injection.py, `FaultJournal.append` (:135-143) raises `Crash` before, inside, or after the real append, and `crash_at` (:153-156) catches it with `pytest.raises`. The dying process therefore unwinds through `Effects.run` and the `with Journal(...)` exit. `Effects.run` (squatch/effects.py:48-65) has no `try`, `except`, or `finally`. When `Crash` propagates, the lines after the failed append (`self._completed[key] = result`, the completion append) just never run. That is the same state a real death leaves. The only code that runs during the unwind is `Journal.__exit__` -> `close()` (squatch/journal.py:108-112). It only closes the file handle, and every record is already fsync'd before the next one starts, so it adds no bytes to disk. The harness also never reads state from the dying process: `restart_and_run` (:159-166) builds a fresh `Journal` and `Effects` over the directory, so in-memory changes made during the unwind cannot leak into what it checks. The byte-offset sweep covers every on-disk prefix whatever the crash mechanism. A subprocess or `os._exit` crash rung would guard against an exception-path writer that does not exist yet, and the anti-bloat law rules that out until one does. This is a different concern from tombstone-000087, which is about fsync fault injection, not how faithfully the harness models death. journal-fsync-fail-closed only adds an in-memory broken flag, which a fresh restart instance never sees, and its scope excludes new harness fault points. No rendered ticket or decision owns this, so a tombstone would be wrong. Reopen if a change gives `Effects.run`, `Journal.append`, `Journal.close`/`__exit__`, or any journal-writing caller an exception-path write (a compensating record, a rollback record, a write or flush on close), or if a harness assertion starts reading state from the crashed process's own instances. In that case, the same change must add a crash rung that kills a child process (subprocess running the effect and dying via `os._exit` or SIGKILL at the write point) and restart-check its directory.

Evidence: tests/test_fault_injection.py:56-57 (Crash), :125-143 (FaultJournal raises at the write point), :153-156 (crash_at catches Crash in-process), :159-166 (restart builds fresh Journal and Effects); squatch/effects.py:48-65 (run has no try, except, or finally; post-append steps are simply skipped on raise); squatch/journal.py:108-112 (__exit__ -> close only closes _fh; records are fsync'd per append per the harness docstring :5-9); open journal-fsync-fail-closed adds only an in-memory broken flag; tombstone-000087 covers the fsync seam, not crash fidelity.
