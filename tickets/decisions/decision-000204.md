No ticket. The behavior is real, but it follows the spec and nothing shows it causing harm. In `Drain._drain` (squatch/drain.py:226, :274), `merged_now` is a list that lives only for the current process. `_handoff` (drain.py:443-457) passes `--config`, `drain`, and repeated `--parked <stem>` flags to the child, and nothing else. The module docstring (drain.py:48-54) and section 18 both say the carried state is the parked set, because the parent's verdicts must hold. Neither says a merge tally is carried. So the child's `_quiescent` and `_halted` lines (drain.py:472-490) count only the merges in their own invocation. That is the same per-invocation scope decision-000203 accepted for the `drain_max_runtime` deadline. Nothing is lost. The `drain_handoff` signal journals the admitted stem, its commit, and the parked set (drain.py:452-454). Every merge is a journaled `to: merged` transition, so `squatch status` and the journal give the full record, and the report is not meant to be the authority (projections are never authoritative, D3). The child also inherits the parent's stdio (drain.py:51), so the operator's terminal shows each hop's `self-upgrade: <stem> ...` line in the same stream. To carry a running tally, the plan would need a new argv flag or signal field, and the child would need new parsing to read it. Under D10 that is speculative: the message gives no evidence (evidence: None), reports no operator confusion, and dates from `bootstrap-ingest`. A tombstone does not fit. decision-000203 covers the deadline, not the merge count. drain-parked-detail and drain-draft-await-confirm change only the `parked:` and draft report lines. No other rendered open ticket, merged Goal line, or decision covers how the merge count is reported across a handoff. Reopen if an operator misreads a multi-hop drain's outcome because of the per-hop count, if the plan adds a rule that drain reports cover a whole handoff chain, or if the handoff starts carrying any other state besides the parked set.
