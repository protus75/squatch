No action. The merged code already has a rule for the unreported case, and it applies that rule the same way everywhere. `_CostMeter.fold` in squatch/driver.py:189-196 treats a None `input_tokens`/`output_tokens` as 0 when it adds them into the single `Cost.tokens` int, and a comment says so ('Unreported usage counts as zero tokens; the usd field still carries the cli est_cost fallback'). The ledger does not copy that folded int. The driver's `effect_completion` cost (driver.py:149-150) and `llmeffect.COST_FIELDS` (llmeffect.py:28, 110) carry the nullable per-call `input_tokens`/`output_tokens` exactly as section 6 types them (SQUATCH_PLAN.md:1072-1073). So an unreported call stays None in the journal, and only the run-level aggregate treats it as zero. Retro reads the ledger in the same way (retro.py:197-198 wraps each value in `numeric(...)` before summing), and so does the watchdog accumulator (watchdog.py:101-102). That gives three consumers with the same None-as-zero aggregation and a verbatim ledger, which leaves nothing to choose between. The one gap is in the plan: the section 5 `Cost` comment (SQUATCH_PLAN.md:922-925) says the effect_completion event 'carries the same fields' but does not state the None-to-0 fold for `tokens`. That is a spec clarification the code already follows, it blocks nothing, and it is not a defect that would regenerate wrong code. A nullable `Cost.tokens` field would add a second representation that every summing consumer would have to handle, and no incident has earned that under the anti-bloat law. No rendered ticket or decision covers token-usage folding. The open config-*, lockfile-*, seams-*, journal-* and effects-completion-result-corruption tickets are unrelated, so a tombstone would be wrong. Reopen if a consumer is found treating an unreported-usage run as a measured zero in a way that misleads a gate or report (for example, the scorecard or watchdog reading 0 tokens as real progress data). If that happens, add one line to the section 5 Cost comment stating the fold rule and keep the ledger nullable.

Evidence: squatch/driver.py:189-196 (fold: `(result.input_tokens or 0) + (result.output_tokens or 0)`, with a comment); squatch/driver.py:149-150 and squatch/llmeffect.py:28,110 (effect_completion carries nullable input_tokens/output_tokens verbatim); squatch/llm.py:55-56 and SQUATCH_PLAN.md:1072-1073 (LLMResult int | None); squatch/retro.py:197-198 and squatch/watchdog.py:101-102 (same None-as-zero aggregation); SQUATCH_PLAN.md:922-925 (section 5 Cost comment, which leaves the fold rule unstated).
