No action for now. The gap is real: `Effects.__init__` (squatch/effects.py:46) uses `self._completed.setdefault(event.key, event.body["result"])`, so when the startup scan meets two completions for one key, the first one wins. No test in tests/test_effects.py covers two completions under one key. The closest test, `test_completed_keys_are_scanned_from_every_segment` (line 198), has only one completion per key. But decision-000014 already found that two `effect_completion` events under one key can only arise from concurrent same-key `Effects.run` calls. It also found that no code path is known to make such calls, because single-flight admission, one-at-a-time scheduling and key-domain scoping prevent them. So this test would pin behavior for a journal state the system cannot currently produce. That is the speculative work the anti-bloat law rules out. decision-000014 also defers the matching change in `run` (switching its last-wins assignment at line 64 to `setdefault`, plus adding an in-flight set). Pinning the scan side alone would cover only half of a first-wins rule that is not settled yet. The test belongs in the ticket decision-000014 prescribes, which should pin first-wins in both the startup scan and `run` together. This is not a tombstone because decision-000014 covers the hazard, not this test gap. It also does not duplicate `effects-completion-result-corruption`, which covers a completion with no `result` field.

Evidence: squatch/effects.py:43-46 (the startup scan uses `setdefault`, so the first completion wins); squatch/effects.py:63-64 (`run` journals the completion and assigns the result, so the last completion wins); tests/test_effects.py has no test that seeds two `effect_completion` events for the same key (tests at lines 131, 180 and 198 each seed one completion per key); decision-000014 (duplicate completions are unreachable today; reopen when any journal holds two completions for one key or when concurrent same-key callers appear, and then fix `run` and the scan together). Reopen on the same triggers as decision-000014, and have that fix ticket include this pre-seeded-segment test.
