No action for now. The message describes the code correctly. `LLMRequest.__post_init__` (squatch/llm.py:41-43) checks `surface` against the module constant `LLM_SURFACES` (llm.py:18-21). Section 5 invariant 6 (SQUATCH_PLAN.md:953) says the `llm_surface` vocab is extended at config load with each host review surface's `name`. `ProviderRegistry` already does this: `self.surfaces = LLM_SURFACES | {s.name for s in config.review.surfaces}` (squatch/providers.py:262), and it refuses unknown surfaces against that extended set (providers.py:276-279). `lint_spec` also accepts an injected `surfaces` set (squatch/specs.py:182-202). So the two allowlists disagree for host surfaces. tests/test_providers.py:280-283 routes a host surface `arch` successfully, but an `LLMRequest(surface="arch", ...)` would raise at construction. However, no production path builds a request for a host surface yet. The only production construction is `Driver.run` (squatch/driver.py:124), and it uses `stage.surface`. Every shipped stage has an engine surface name. Nothing in squatch/ reads `review.surfaces` except the registry, and nothing reads `rules_doc` except its config field (config.py:106). Host-surface review dispatch (section 7, SQUATCH_PLAN.md:1111) has not been built. The mismatch also fails closed: a host-surface request would raise a loud ValueError, not be admitted silently. A standalone ticket now would change a kernel contract with no consumer, which the anti-bloat law rules out. It is also the wrong shape. Building a second config-fed set on the request would leave two surface validators, and that is a dual-path. The better fix is chosen when a consumer exists: either the request takes its allowed set from the one config-derived vocab the registry already owns, or the construction-time check becomes the engine-set check and the registry's config-extended check stays the only authority for host names. This follows how decisions -000064, -000067 and -000070 handled a latent gap with no consumer. No rendered ticket or decision covers the `llm_surface` vocab on `LLMRequest`. The open config-* tickets cover empty paths, null list elements, numeric bools, gate-code vocab and path precedence, not the surface vocab. config-gate-code-vocab is about `GATE_CODES`, not `LLM_SURFACES`. So a tombstone would be wrong. Reopen when any ticket builds host-review-surface dispatch through the Driver (or otherwise constructs an `LLMRequest` whose surface comes from `config.review.surfaces`). That ticket must fix this in the same change, so a host surface that routes can also be requested. It must also pin the fix with a test that dispatches a config-declared surface end to end.

Evidence: squatch/llm.py:18-21 static LLM_SURFACES; llm.py:41-43 __post_init__ checks against it; squatch/providers.py:262 and :276-279 registry vocab extended from config.review.surfaces; squatch/specs.py:182-202 injectable surfaces; squatch/driver.py:124 is the only production LLMRequest construction and uses stage.surface; tests/test_providers.py:54, :183, :280-283 route host surface `arch` with no request built; SQUATCH_PLAN.md:953 (invariant 6) and :1111 (host surfaces run under the one driver); nothing in squatch/ dispatches a host review surface.
