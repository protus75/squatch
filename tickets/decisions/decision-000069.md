No action. The message describes the driver correctly, but the choice it asks for has already been made in the code and in every spec, and nothing is failing. squatch/driver.py `_parse` (lines 206-246) is the only output parser. It accepts one JSON object, allowing either a single ```json fence or raw-decodable text whose surrounding prose has no braces. It then stamps `produced_by_spec_version`/`produced_at_sha` (line 114, invariant 1) and validates against `stage.emits`. When the output is not JSON, is not an object, or fails the schema, it returns a finding with the paved road 'emit exactly one JSON object with the fields of <emits>'. That finding goes back through the bounded re-prompt, and shakeout-driver already pins that re-prompt to an `invalid_artifact` terminal. There is no per-stage parser and nothing needs one. All eight shipped specs already require exactly this form in their `## Output format` section: implement.md:99, review.md:78, triage.md:52, diagnose.md:48, retro.md:25, rework.md:39, author.md:50 and requisition_review.md:59 each say 'exactly one JSON object'. A spec-lint rule that checks the wording of Output format would be a second enforcement path over prose. The driver already enforces the real contract at runtime and fails closed with a paved road. No spec has drifted and no incident has come from this, so the anti-bloat and no-dual-path laws rule it out. What remains is wording in the plan: section 8 (SQUATCH_PLAN.md:1115) names the fixed `Output format` section but does not say its content is one JSON object that the driver parses and stamps. The merged code and specs already follow that rule, it blocks nothing, and a plan regeneration would not produce a per-stage parser because the specs it would regenerate all name the JSON-object form. This is the same handling as decision-000053, -000062 and -000064 for small plan/code wording gaps. No rendered ticket or decision covers LLM output encoding. The open config-*, gates-*, journal-* and seams-* tickets are unrelated, so a tombstone would be wrong. Reopen in any of these cases: a new or regenerated spec's Output format names a non-JSON-object form; a surface needs output that one JSON object cannot carry; or the operator judges the section 8 wording to be a plan defect. For that last case the fix is one clause in section 8: 'Output format names exactly one JSON object carrying the emits artifact's fields minus the driver-stamped provenance.' Add that clause to the plan, not to spec lint.

Evidence: squatch/driver.py:114 (provenance stamp), :206-246 (_parse: one JSON object, fence/raw-decode tolerance, dict check, emits.model_validate, paved-road findings); squatch/specs.py:31 SPEC_SECTIONS and :277-314 _lint_body (checks section presence, not content); specs/{implement:99,review:78,triage:52,diagnose:48,retro:25,rework:39,author:50,requisition_review:59}.md all say 'exactly one JSON object'; SQUATCH_PLAN.md:1115 section 8 names Output format without pinning encoding; merged shakeout-driver pins the invalid-output re-prompt to invalid_artifact.
