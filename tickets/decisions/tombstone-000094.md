The serve `kill <run>` path this message lists as still to build is already merged and wired from the spawn hook to the serve verb. There is no separate pgid-passing chain left to add. The pieces: (1) `kill-executor-abort` added `Driver.abort_active` (squatch/driver.py:97-103). It cancels the active invocation task and waits for it to unwind. (2) That cancellation reaches `LLMEffect._call` (squatch/llmeffect.py:64-68), whose `CancelledError` branch runs `_abort`. `_abort` calls `self._llm.abort_current()` and only then cancels and waits for the call task (:101-104). (3) `CliClient.abort_current` (squatch/providers.py:485-488) calls `kill_group` on the pgid that `on_spawn`/`_bind` published (:443, :482-483). The `finally` at :457-458 clears that binding when the call returns, so a pgid is used at most once and never after its call ends. (4) `kill-worker-stop` / `kill-cli-activation` added `kill_worker_stop_consumer` (squatch/daemon.py:508-531), which calls `driver.abort_active()` on a `kill` request before stopping the worker tasks. `serve-activation` composes it into production serve (squatch/serve.py:142). Because the cancel runs through the existing Driver -> LLM effect -> provider stack, providers, stages and serve never need to pass a run-to-pgid binding along explicitly; the binding stays inside the client by design. The message is a bootstrap-ingest note written before these merges and is now stale. Reopen if a provider path launches a subprocess outside `CliClient.call`'s `on_spawn` binding, if a `kill` with an active CLI call leaves a live process group, or if `Driver.abort_active` stops cancelling through `LLMEffect`.
