No ticket. The defect is real in the code but cannot happen in production. `CliClient._pgid` (squatch/providers.py:401) holds one pgid. `_bind` (:482-483) sets it and the `finally` at :457-458 clears it unconditionally. If two `call`s overlapped on one instance, the first call's `finally` would erase the second call's binding, and `abort_current` (:485-488) would then do nothing. But the message's premise, that Phase 3 dispatches two runs on a shared client, does not hold. Dispatch is single-flight by design: D2, SQUATCH_PLAN.md:1143 and :1327, and the `_in_flight: str | None` slot in squatch/scheduler.py:21-53. The concurrent worker pool is an explicit D10 deferral (SQUATCH_PLAN.md:1437), returning only on measured starvation or contention after cutover. In production serve, the only stack that runs concurrently with dispatch is Triage, and it builds its own separate `CliClient` (squatch/serve.py:232-235), so it shares no pgid slot with the Driver's client (:217-219). The kill path that tombstone-000094 confirmed (Driver.abort_active -> LLMEffect._abort -> CliClient.abort_current) therefore always sees one call per client. Adding a `{run: pgid}` map now would build machinery for a subsystem that does not exist yet, which the anti-bloat law and the 'simplest thing' rule forbid. The message itself says nothing stalls today. No rendered work covers this. tombstone-000094 covers whether the kill chain exists, not per-client concurrency, and seams-kill-transport-timeout covers escaped descendants holding pipes. A tombstone would therefore be wrong.

Evidence: squatch/providers.py:401, :443, :455-458, :482-488 (single pgid slot, cleared unconditionally in finally). squatch/scheduler.py:1, :21, :49-53 (single-flight dispatch). squatch/serve.py:217-219 vs :232-235 (Driver and Triage each construct their own CliClient). SQUATCH_PLAN.md:1143, :1327 (D2 single-flight), :1437 (worker pool deferred to section 18). Reopen when any of these happens: the section 18 concurrent worker pool, or any `workers`/parallel-dispatch key, is admitted; a single CliClient instance is passed to two components that can await `call` concurrently (for example, Triage or Rework reusing the Driver's client while a dispatch is in flight); or a `kill` with an active CLI call leaves a live process group. In that case, change the binding in providers.py to a per-call one (cleared only if it is still the call's own pgid, or keyed by request) in the same change, with a test of overlapping calls on one client.
