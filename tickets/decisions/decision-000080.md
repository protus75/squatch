No action now. The message is accurate, but the gap is in the plan's wording only, and the code already keeps the value in one place. Section 8 (SQUATCH_PLAN.md:1118) asks for ONE engine-owned, conservative character-count bound keyed by resolved effort and forbids stage-local bounds, but it gives no numbers. Section 6 lists other engine constants (the journal roll at 64 MiB/24h, the 3s background fsync, the 16 MiB x 4 engine log, the 60s spill wait) and does not list this bound. The code meets the 'one place' goal: `RENDER_BOUND_CHARS` (squatch/specs.py:47-51) is the only definition. Its comment gives the derivation: about 4 chars per token against a 200k-token context, minus thinking headroom that grows with effort. Every consumer reads that mapping, not a copy: the render check at specs.py:145, requisition's feasibility measurement at requisition.py:281, and every seeded-phase test through `RENDER_BOUND_CHARS['max'] * REQ_RENDER_HEADROOM`. So if a provider's context changes, the code is re-derived by editing one line. The only real risk is a plan regeneration choosing different numbers, because the plan does not pin them. Engine tickets do not author plan prose. This is the same kind of plan/code wording gap that decisions -000072, -000074 and -000079 handled. A ticket would only restate an existing constant, and the anti-bloat law rules that out. No rendered ticket or decision covers the render-bound values. Decision-000079 covers the Outcome for an over-bound render, not the bound's size, and the open config-*, gates-*, journal-*, seams-*, lockfile-* and effects-* tickets are unrelated, so a tombstone would be wrong. Reopen in three cases: a plan regeneration rebuilds specs.py with different values; a provider whose context bound differs from 200k tokens is routed; or the operator treats the missing values as a plan defect. The fix then is to add the four per-effort values and their derivation to section 6's engine-constants list (or to section 8 at :1118), with specs.py:50 as the code that renders them.

Evidence: SQUATCH_PLAN.md:1118 (bound keyed by effort, no values); section 6 engine constants at SQUATCH_PLAN.md:975, :977, :1015, :1084 (render bound not among them); squatch/specs.py:47-51 (RENDER_BOUND_CHARS low 400k / medium 320k / high 240k / max 160k with derivation comment); squatch/specs.py:145 and squatch/requisition.py:281 (only production consumers, both read the one mapping); tests/test_specs.py:342-359 (pins key set and ordering, not literal values).
