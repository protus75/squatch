## Summary
The report, registration, and operator GO path meet the ticket's structure and the checks are green. Three problems remain: the GO-grade run shares effect keys with ordinary harness runs, so it can replay unrelated cached review replies; the $5.00 cap is enforced only after a call has already overspent; and the operator GO signal carries a made-up zero-catch summary.

## Findings
- correctness_review at eval/harness.py:480: run_go_grade drives the review stage with the same key parts as the ordinary run(): ticket=None, so stem is the surface name 'review'; run_seq comes from _run_seq; and attempt runs 1..N. LLMEffect keys are effect_key('llm', stem, run_seq, surface, attempt, call_seq), with no prompt hash. An ordinary run that ends UNSCORED appends no signal, so run_seq does not advance. A following go-grade run then replays that run's cached fixture replies (and their costs) as the verdicts for planted-01..k, and scores planted defects against unrelated answers. The reverse also happens: a go-grade run refused by the cap leaves keys that a later ordinary run replays. The only test covering this (test_go_grade_after_recorded_baseline_uses_fresh_effect_keys) covers just the case where a signal was recorded in between. (paved road: Give the go-grade lane its own key namespace. For example, pass a distinct stem (ticket='go-grade' or a dedicated stage surface/stem) or a disjoint attempt range, so its effect keys can never match an ordinary harness run at the same run_seq. Add a test: an ordinary run that ends UNSCORED, then run_go_grade, must still call the model for every planted fixture.)
- correctness_review at eval/harness.py:476: The fixed USD 5.00 cap can be exceeded. Before each call, _reserve_call only checks headroom against the most expensive call seen so far (per_call_bound). A review call that costs more than any earlier call can push spend past $5.00, and the check after the call only raises Unscored once the money is spent. The ticket's Definition of rejected lists overflow, and no test covers a call that costs more than the running maximum. I'm unsure whether a hard pre-call bound is achievable with the current LLM seam, but as written the cap is best-effort, not fixed. (paved road: Reserve against a fixed, configured per-call upper bound (for example, derived from the tier's max tokens and price) rather than the largest call observed. Refuse before any call whose bound exceeds the remaining headroom. Add a test where a later call would cost more than every earlier call and assert that no call is made past the cap.)
