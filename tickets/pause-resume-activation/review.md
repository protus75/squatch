## Summary
The production wiring mostly works: decisions are journaled before holds change, holds come back after a restart, and a release only clears the matching hold. But the new tests leave several acceptance criteria unproven, the paused drain polls the journal every 10 ms through a raw sleep that bypasses the clock seam, and the operator has no way to learn the hold id that resume requires.

## Findings
- correctness_review at tests/test_control_cli.py:20: Criterion 1 is only partly met. (a) The live-lock test publishes only `pause`; no test publishes `resume` under a live engine lock. (b) `test_stale_and_prehold_release_do_not_release_a_direct_pause` does not test a stale lifecycle. It builds a throwaway `ControlInbox` with a fresh lifecycle and sends a release addressed to that same lifecycle, so the request is rejected only because its random hold_id does not match. It also never goes through the CLI. (c) Nothing tests a release published before the hold existed, i.e. a `resume` request sitting in the inbox before the `pause` that mints the hold is consumed. (paved road: Add CLI-level tests for: resume published under a live lock with no journal write; a request addressed to an earlier or ended lifecycle that is decided `stale` and leaves the hold in place; a release published before the pause in the same or an earlier snapshot, with the later hold still active.)
- correctness_review at tests/test_daemon_composition.py:70: Criterion 2 is not met. The new test calls `compose_daemon_control` and `DispatchPause` directly, so it never exercises routing through `__main__` `_drain`/`_control_factory`/`Drain._wait_for_offer`. It also asserts neither non-preemption (admitted or in-flight dispatch is not interrupted by a pause) nor decision-before-mutation through the shared boundary. It covers only restart rehydration and matching release. (paved road: Drive `main(['drain'])` or a `Drain` built with the production `_control_factory` over a real journal. Publish pause and resume mid-drain and assert: an in-flight dispatch completes; the `control_decision` accepted event comes before the `control_hold` event; dispatch stays blocked until the matching release; a restart reuses the hold.)
- correctness_review at squatch/__main__.py:168: While paused, `wait_for_control` loops `inbox.consume(...)` plus a raw `asyncio.sleep(0.01)`. Each `consume` calls `_decisions()`, which re-reads the whole journal, so a paused engine rescans the entire journal about 100 times a second for as long as the pause lasts. The raw sleep also bypasses the injectable clock seam, so engine timing cannot be tested without real time. (paved road: Wait through an injectable sleep or clock seam at a bounded cadence (or a filesystem-change wait) passed into `_control_factory`, and use a poll interval sized for operator latency (e.g. seconds), not 10 ms.)
- correctness_review at squatch/__main__.py:187: `resume` requires `--hold-id`, but neither path tells the operator the hold id. Both print only the request id, and nothing added here (status or elsewhere) shows active holds. To resume, the operator has to dig through the journal for a `control_hold` signal. That leaves a pause with no reachable release, which is fail-stuck rather than fail-closed. (paved road: Print the minted hold id on direct `pause` (and on `resume` when it is refused). For the live path, show the active hold id where the operator can read it, e.g. `squatch status` projecting the latest unreleased `control_hold`. That needs a fence change if status sits outside the fence, so otherwise print it from `_control` by reading the journal.)
- correctness_review at squatch/__main__.py:180: Under `LockHeld`, the CLI assumes the lock holder is a draining engine and addresses the request to the latest `control_lifecycle` signal. That signal may come from a dead process: every direct CLI run and every past drain appends one. If the lock is held by `run`, `triage`, or `new`, which never consume control, the CLI still prints `published pause`. The next drain mints a new lifecycle (when no hold is active) and decides the request `stale`. The operator is told the pause was published, but it silently never takes effect. I am not certain the plan intends that stale outcome. (paved road: Publish only when the holder is a live control consumer: e.g. the drain journals its lifecycle together with its lock instance_id, and the CLI checks that against `LockHeld.holder`. Otherwise refuse with a paved road, such as retrying once a drain is running or waiting for the current verb to finish.)
