## Summary
The diff adds CLI verbs and merge-queue hold triggers, but it never wires pause/resume or the admission hold into the production daemon composition. It also gives the merge queue a second ControlInbox that competes with the dispatch inbox, and it leaves the required test_daemon_pause.py migration undone.

## Findings
- correctness_review at squatch/mergequeue.py:129: MergeQueue builds its own default ControlInbox (`AdmissionHold(ControlInbox(self._journal.dir.parent, ...))`), which gets its own fresh uuid4 lifecycle and consumes the same `<state>/control` directory as the daemon's dispatch inbox. The two consumers race over one directory. A pause or release meant for the dispatch lifecycle can be consumed first by the merge queue's inbox during `allow()`. That inbox journals it as `stale` (lifecycle mismatch) and removes the file, so the dispatch release is lost. The reverse also happens: an admission-hold release can be eaten by the dispatch inbox. That breaks 'Only resume releases the current hold' and routing 'through the shared control boundary'. (paved road: Make `hold` a required dependency and inject the single daemon-composed ControlInbox (from compose_daemon_control) into both DispatchPause and AdmissionHold. Use one mutate callback that routes a release to whichever hold owns that hold_id, so the engine has one consumer and one lifecycle.)
- correctness_review at squatch/__main__.py:94: Production composition is not wired. `_drain` and the daemon path still call compose_daemon_dispatch without `pause=`/`wait_for_control=`, and no DispatchPause, control consumer or AdmissionHold is passed into the production merge queue. `squatch/daemon.py` is not changed at all. A live engine therefore never acts on the requests the CLI publishes. The new composition test builds the graph by hand, so it does not prove 'real production pause/resume routing'. (paved road: In the production drain/daemon factory, compose the control inbox once and pass DispatchPause plus control_consumer into compose_daemon_dispatch. Pass the same inbox's AdmissionHold into compose_merge_queue. Then prove it through main()/the production factory in tests/test_daemon_composition.py.)
- correctness_review at squatch/__main__.py:197: The no-engine path defeats identity checks and cannot release anything it held. `inbox.lifecycle = request.lifecycle` accepts any lifecycle the operator types, so a stale lifecycle can never be rejected. The DispatchPause hold is also only in memory and disappears when the process exits. A direct `pause` therefore has no lasting effect, and a later direct `resume` can never match a real hold (the test's 'stale' only reflects a random hold_id). The code also calls the private `pause._apply`. (paved road: Derive the direct-mode lifecycle and current hold identity from durable journal state (the last accepted pause/hold decision), not from the request. Reject a mismatched lifecycle as stale, and have direct resume release only the journaled current hold. Expose a public apply method instead of `_apply`.)
- correctness_review at tests/test_daemon_pause.py: Acceptance criterion 4 requires migrating the dormant-activation assertions in tests/test_daemon_pause.py while keeping its accounting-order tests. The file is not in the diff, so its construction-dormancy contract is left as it was. (paved road: Update tests/test_daemon_pause.py so its dormancy assertions reflect the activated production path, and keep the accounting-order tests.)
- correctness_review at squatch/mergequeue.py:205: Red-streak counting resets to `(stem,)` when a ticket already in the streak goes red again. The ticket asks for three consecutive DISTINCT tickets going integration-red, with a reset only on green. A re-red from a retried ticket (for example A, B, A-retry, C) erases progress, so a run of red tickets can avoid the hold. I am not certain of the intended semantics for repeats. (paved road: Reset only on green. Skip a repeat stem (or keep it counted once) rather than restarting the streak, and add a test for the repeated-stem case.)
- correctness_review at squatch/mergequeue.py:149: A held admission returns `outcome="gate_failed"` with a finding. Downstream this is treated like a real gate failure of the candidate, which can fail or rework a ticket whose only problem is the global hold. That conflicts with 'Neither cancels in-flight work'. I have not confirmed how the pipeline consumes gate_failed here. (paved road: Block admission by waiting on the hold (as DispatchPause does at dispatch), or return a distinct non-failure outcome that the pipeline re-queues, rather than a candidate gate failure.)
