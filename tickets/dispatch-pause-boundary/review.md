## Summary
The daemon-side pause boundary is sound. The ControlInbox hold-discard supersession works, and the ordering before admission is correct. In the drain hook, though, a pause ends the whole drain instead of holding the pending offer until its release, and nothing tests the drain half of acceptance criterion 2 (a release lets the pending offer through without spending anything while paused).

## Findings
- correctness_review at squatch/drain.py:213: When `allow_offer()` returns False, `_drain` does `return EXIT_OK` and the session closes. The hold is minted by an in-memory `ControlInbox` whose lifecycle is a fresh `uuid4()` for each drain session. After the drain exits, no release can ever match that hold: the next run gets a new lifecycle, so the old release is judged stale. This makes the drain-side pause a one-shot stop. It is not a hold-bound hold that 'allows exactly the pending offer' on release, so the drain half of the hold's release path cannot be reached. Exiting with EXIT_OK also reports a paused run as a clean drain. (paved road: Keep the session open while paused. Wait on the injected clock/seam and re-consume the inbox (`await pause.allow_offer()` in a loop) until the matching release lands. Then continue to the same `ticket`/`offer` and draw the retry only after release. Alternatively, if exiting is the intended design, state that in the plan and give the pause a release path that survives the lifecycle.)
- correctness_review at tests/test_drain.py:167: Acceptance criterion 2 requires `tests/test_drain.py` to prove that 'release allows exactly the pending offer without spending while paused'. `test_pause_blocks_fresh_and_retry_offers_before_their_durable_accounting` covers only the refusal. It asserts `fake.calls == []` and `draws == []`. It never publishes a matching release and never asserts that exactly one dispatch follows, with exactly one retry draw in the parked case. The release half of the criterion is untested. (paved road: Extend the parametrized test so that, while paused, it publishes a release bound to `pause.hold_id` (for example via the injected inbox or a scripted clock/seam hook). Assert that the paused ticket is then dispatched exactly once, that the parked case records exactly one retry draw after the release, and that no draw or transition was recorded before it.)
- correctness_review at tests/test_daemon_pause.py:26: Acceptance criterion 3 asks for a direct test that the decision is journaled before any mutation. `test_pause_decision_is_journaled_before_an_offer_can_mutate_admission` checks that decisions exist and that no admission happened, but it never records when the governed mutation happened relative to the journal append. A mutation that ran before the 'accepted' append would also pass. I'm flagging this with moderate confidence: ControlInbox enforces the order internally, but the criterion asks for a direct proof. (paved road: Wrap the mutation (or `DispatchPause._apply`) in a probe that reads `journal.read()` at mutation time. Assert that the `control/<request_id>` 'accepted' decision is already present when the hold is set, and that the applied marker follows it.)
