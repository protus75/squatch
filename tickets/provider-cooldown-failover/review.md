## Summary
The cooldown timer and the single shared provider payload are wired correctly, and the refactor stays inside the fence with green checks. But when a single configured candidate hits its quota, the ticket does not park. Every dispatch while the cooldown is live fails as an unclassified infra_error, which uses up the ticket's infra cap. The attempt that hits the quota is also lost, even when another eligible candidate exists.

## Findings
- correctness_review at squatch/providers.py: ProviderRuntime.resolve raises a bare RoutingError('no eligible candidate; cooling down: ...') when every candidate is cooling down. That error carries no failure_class and no paved_road. Driver.call catches it and returns an infra_error terminal with no classified finding (driver.py:138-145). Runner then calls consume(..., cap=INFRA_CAP) (runner.py:359). So for a single-candidate route, the scheduler keeps dispatching the ticket during the cooldown window. Each dispatch uses up one infra-cap slot and may send the ticket to the reject route before timer_fired makes it eligible again. The ticket requires that a single configured candidate that exhausts quota 'arms its cooldown and parks'. The new test only checks that RoutingError is raised at the client level. It never checks what the scheduler or run record does, so the 'parks' criterion is unmet in production. A plain RoutingError is also documented as a config/setup refusal, so this reuses a closed error class for a different meaning. (paved road: Make an all-candidates-cooling-down route a real park: either a classified ProviderError (failure_class 'quota_exhausted' with a paved_road naming the cooldown deadline) that the outcome routing treats as a hold rather than infra-cap consumption, or a dispatch-time eligibility check that skips the ticket until the cooldown Timer fires. Add a test in tests/test_provider_cooldown_failover.py that drives a single-candidate quota exhaustion through the runner. It should assert that no INFRA_CAP is consumed while the cooldown is live and that the ticket becomes dispatchable after timer_fired.)
- correctness_review at squatch/providers.py: Failover only happens on the NEXT call. In CliClient.call, the call that gets quota_exhausted arms the cooldown and then re-raises the ProviderError. It does not retry the next eligible configured candidate. That attempt ends as infra_error and uses up INFRA_CAP (runner.py:359) even though an eligible candidate exists. This works against the ticket's goal that 'an eligible configured candidate can keep work moving' and its instruction to 'try configured candidates in order, skip a candidate whose cooldown is live'. It also counts against the same cap a ticket might have used for a real infra failure. I'm not sure this is a defect. The ticket may accept failover only on the next call. But in production this means one lost attempt per quota hit on every stage. (paved road: After cool_down(provider), let CliClient.call move on to the next non-cooling-down candidate from ProviderRuntime within the same call, and raise only when none is eligible. Or state why next-call failover is enough, and make sure the quota-hit attempt does not consume INFRA_CAP. Extend the ordered-failover test so the first request itself is served by the later candidate, or so it asserts that no cap was consumed.)
- correctness_review at squatch/stages.py: When watchdog=True, WatchdogLLM.call resolves the route through the shared ProviderRuntime (watchdog.py:228). Then the inner CliClient.call resolves it again on its own. Timers.pending can fire an expired cooldown between the two resolves. If it does, the watchdog's cost basis and served identity (row.name, resolved.model) can name a different provider than the one that actually ran. That makes the watchdog evidence for a failed-over call inconsistent. This is uncertain: the window is small, but it opens exactly at the moment a cooldown resets. (paved road: Resolve once per call. Either pass the Resolved chosen by the watchdog down to the client, or have the watchdog read the served identity from the client's result or events instead of resolving again.)
